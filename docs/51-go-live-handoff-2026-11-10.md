## 2. The issue list, by severity (owner's wording: Sev 1, Sev 2, "shi")

### Sev 1: fix before go-live
1. **Pause does not stop messages already queued.** Start turns the whole audience (up to the dispatch batch, `limit: room` in `apps/gateway/src/work.ts` around line 412) into queued messages within seconds. `setCampaignStatus` in `packages/core/src/campaign-actions.ts` only flips the status on Pause; on Cancel it withdraws queued messages that have not started (R-020). `laneCandidates` in `packages/core/src/antiban/lane-state.ts` never looks at the campaign's status. Evidence: 4 queued 11:39:37, Pause 11:39:45, three more sent 11:39:49, 11:39:56, 11:40:31. Fix direction: a paused campaign's queued messages are held (reason `campaign_paused`) or withdrawn, and released on Resume. Repro: `wa-testers\run\wave4.mjs` (P2).
2. **The AI can wrongly opt a person out.** `looksNegative` in `packages/core/src/antiban/optout.ts` (line 42) runs on every inbound message with no keyword match (`opt-out.ts` lines 83 to 85). Against the live model, "flood 10" was read as an opt-out (1 in 32 harmless texts; all 6 real opt-outs caught). The person gets do-not-contact and "We will not message you again"; agents are blocked and only an admin can clear it (R-034). Fix directions: require more than the model's word (clear phrase, or a short confirm), let an agent undo a classifier opt-out, show "marked by the AI". Repro: `wa-testers\run\probe-classifier.mts` (run with `node_modules/.bin/tsx`).
3. **Two admins demoting or disabling each other at the same moment leave no admin.** 25 of 25 rounds. `changeMember` in `packages/core/src/team.ts` (lines 53 to 111) locks only the target's membership row and counts the other admins from committed data. Fix direction: one lock per organisation's admin set (advisory lock, or lock all admin rows) before counting. Tests: the two `[R-041]` `it.fails` in `races-and-abuse.test.ts`. The only code that writes roles or disables members is `changeMember`.
4. **The AI hand-over shows the internal login to customers:** "a colleague from live@test.local (+91 99641 22631)". Same as the AI-template item about naming the hand-over person (docs/49). Find where the hand-over person is named (AI reply / template code) and use the team member's display name.

5. **In an AI campaign, the AI does not answer a new person's first reply when something was held back for it (confirmed for a picture; the same path covers a link).** With "send the picture after they reply" on (the default), the held picture is queued 2 seconds after the reply, and `autoReply` in `packages/core/src/ai-reply.ts` skips an inbound message as `superseded` when ANY newer message exists in the chat (`newerExists`, lines 109 and 202 to 206; checked again after the model call, around line 146). The gateway queues the follow-up first (`apps/gateway/src/main.ts` around line 238) and only then calls `autoReply` (around line 265), so the picture counts as "someone already answered". The person gets the picture and no answer until they write again. Evidence (live, second run): inbound 12:37:57, picture queued 12:37:59, no AI message; a second reply at 12:45:04 was answered at 12:45:08. Two other phones got no AI text in 8 minutes. The same split holds a link in the text for new chats (`splitFirstMessage`), so an AI campaign whose message has a link is likely hit too (not tested). Fix directions: ignore the campaign follow-up (a `system` campaign message) in `newerExists`, or run the AI answer before queueing the follow-up. Standard (non-AI) campaigns and AI campaigns with the picture sent in the first message are fine. Repro: `wa-testers\run\pic-setup.mjs --api ai wait test.jpg` then `pic-wave.mjs <id> wait ai` (evidence kept in `pic3b.out` and `pic3b.ev`).

### Sev 2
5b. **Two agents sending the first message in an unowned chat both go through** (25 of 25 rounds). `claimIfUnowned` in `apps/api/src/routes/messages.ts` (lines 78 to 93) ignores a claim that updates no row; the owner check (around line 1007) is a plain SELECT. Same code on the attachment route (around line 940). Fix: make the claim the rule (if it updated nothing, re-read the owner, refuse a non-admin with 409 `THREAD_ASSIGNED`). Test: `[R-042]`.
6. **A repeated send creates two messages.** No repeat guard in the API (retry, second tab, integration retry). Proposal: an `Idempotency-Key` header with a unique index (needs a migration); the Inbox generates one per Send. The Inbox itself sends one message for human double-clicks (30, 80, 150 ms apart) but two when two clicks land in the same instant. Test: `[R-043]`.

8. **Quiet hours do not hold a campaign message to anyone who wrote in the last 24 hours.** `laneCandidates` files any queued message as `reply` when the chat has an inbound message in the last 24 h (the priority `CASE`, `lane-state.ts` around line 51), and `policy.ts` (line 79, AC-7.5) holds only `campaign` and `ai`. Test: quiet hours set to 10:37 to 13:37 at 11:37; a campaign to four people who had just written went out 11:38:40 to 11:39:16. Repro: `wave4.mjs` (P1). Fix direction: a message with a campaign id is a campaign message for quiet hours, whatever the chat history.
9. **A landline is accepted as a phone on import and tagged with everyone.** The send path refuses it (422 `NOT_REACHABLE`, `messages.ts` line 1085); import does not. "Message them now" on the import result includes it. The sender checks WhatsApp registration, but a landline can be on WhatsApp.

Saving different fields at once is safe (merged in the database); the same field at once is last write wins. Decision: send only what changed, or refuse a stale save. Test: `[R-044]` (characterisation).
14. **A corrupt picture is accepted as a campaign picture.** A PNG cut to 100 bytes returned 201: the type is judged from the first bytes only. Not tested at send time.
